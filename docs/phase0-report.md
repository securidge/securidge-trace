## 3. 조사 결과

### 3.1 화면(GUI) 방식 — 결정 필요 (D1)

| 방식 | 추가 설치 없이 실행 | 한글 | 라이선스 | 비고 |
|---|---|---|---|---|
| **egui / eframe** 0.37 | 가능 (실행 파일 하나) | 기본 글꼴에 한글이 없어 **시스템 글꼴(맑은 고딕)을 불러와야 표시됨.** 한글 입력기(IME) 안정성은 **확인하지 못함** | MIT OR Apache-2.0 | 가장 단순. 디자인 자유도는 낮음 |
| **Slint** 1.19 | 가능 | 미확인 | GPL-3.0 / 로열티 프리(Slint 사용 사실을 표시해야 함) / 유료 | 우리 코드는 MIT·Apache로 둘 수 있으나 배포물에 고지 의무가 생김 |
| **Tauri** (WebView2) | **조건부.** Windows 11은 내장, Windows 10은 대부분 설치돼 있으나 일부는 없음 | 브라우저 엔진이라 문제없음 | MIT OR Apache-2.0 | HTML 보고서와 화면을 같은 기술로 만들 수 있음. 설치 프로그램 없이 배포하면 WebView2가 없는 PC에서 실행 불가 |

**권고:** egui로 "언어 전환 + 한글 입력 칸 하나"만 있는 시험판을 만들어 Windows 10·11에서 직접 입력해 본다. 한글 조합 입력이 정상이면 egui로 확정, 아니면 Slint로 간다. Tauri는 "USB에 담아 어느 PC에서나 바로 실행"이라는 요건과 충돌할 수 있어 3순위다.

**이 환경에서는 시험할 수 없다**(4장 참고). 그래서 화면 뼈대는 이번에 만들지 않았다.

출처: docs.rs의 egui 글꼴 관련 crate 설명, Slint LICENSE.md, Microsoft Learn "Distribute your app and the WebView2 Runtime"

### 3.2 잠긴 파일을 읽는 방식 — 결정 필요 (D2)

실행 중인 Windows는 레지스트리 하이브 등을 잠가 두어 일반적인 복사가 안 된다. 아래 비교는 **공개 자료와 구조에 근거한 분석이며, 실제 Windows에서 측정한 것이 아니다.**

| 방식 | 대상 PC에 남기는 변화 | 권한 | 걱정되는 점 |
|---|---|---|---|
| **A. 볼륨을 직접 읽어 NTFS 해석** (`\\.\C:` 읽기 전용) | 쓰기 없음 | 관리자 | 읽는 도중 파일이 바뀌면 내용이 어긋날 수 있음. 백신·EDR이 디스크 직접 읽기를 의심 행위로 볼 가능성(미확인). 구현 난이도 중상 |
| B. 볼륨 섀도 복사본(VSS) 생성 | **스냅샷을 새로 만들므로 변화가 남음** (섀도 저장 공간, 이벤트 로그) | 관리자 | 일관된 시점의 사본을 얻는 장점. "대상 PC를 최소한으로 건드린다" 원칙과 충돌 |
| C. Windows 레지스트리 API | 다른 사용자의 하이브를 읽으려면 불러와야 하고 이는 변화를 남김 | 관리자 | 레지스트리만 해결. 이벤트 로그·브라우저 DB는 별도 방법 필요 |

**권고:** A. 원칙에 가장 잘 맞는다. 읽는 도중 바뀌는 문제는 "두 번 읽어 해시가 같은지 확인"으로 줄인다.

### 3.3 배포 걸림돌 — 결정 필요 (D3)

Microsoft 문서 기준으로 확인한 사실:

- 서명되지 않은 실행 파일은 "Windows의 PC 보호" 경고가 뜨고, 사용자가 "실행"을 눌러야 한다. 회사 정책으로 아예 막혀 있을 수도 있다.
- **서명을 해도 새 파일은 평판이 쌓일 때까지 경고가 뜬다.** 예전에는 EV 인증서가 경고를 바로 없애 줬지만 지금은 아니다.
- Microsoft의 서명 서비스(Azure Artifact Signing, 월 약 10달러)는 조직은 미국·캐나다·EU·영국, 개인은 미국·캐나다만 가입할 수 있다. **한국에서는 쓸 수 없으므로** 인증 기관의 OV 인증서(연 150~300달러 수준)가 대안이다.

**결론:** 인증서를 사도 초기에는 경고가 뜬다. 그러므로 (1) 도움말 첫 화면과 USB에 함께 담는 안내문에 "경고가 떴을 때 누르는 순서"를 그림으로 넣는 것이 필수이고, (2) 서명은 "게시자 이름이 표시되어 신뢰를 준다"는 효과로 보고 실제 배포 전에 결정하면 된다. 백신 오탐 가능성은 실제 실행 파일이 나온 뒤에 시험해야 한다.

출처: Microsoft Learn "SmartScreen reputation for Windows app developers", "Code signing options for Windows app developers"

### 3.4 구현하면서 발견한 설계 문제

1. **"파일을 언제 열었는가"는 바로 가기 파일 자체의 수정 시각에서 나온다.** 이 값은 파일 시스템 값이라, 폴더를 단순 복사해서 수집하면 수집 시각으로 바뀐다. 따라서
   - Phase 3의 수집본에는 **원본 파일의 시각(생성·수정·접근)을 따로 적은 목록(manifest)**이 반드시 있어야 한다.
   - 지금의 오프라인 폴더 입력은 열람 시각의 신뢰도를 "중간"으로 두고 주의 문구를 붙였다.
2. **대상 PC의 ANSI 코드 페이지를 알아야 한다.** 유니코드 경로가 없는 바로 가기는 코드 페이지(한국어 949)로 풀어야 한다. 지금은 옵션(기본 949)이고, Phase 2에서 SYSTEM 하이브의 값을 읽어 자동으로 정해야 한다.
3. **공개 샘플에는 USB에 있던 파일의 바로 가기가 없다.** 이 도구의 핵심 시나리오(이동식 드라이브 + 볼륨 시리얼)는 가상 머신에서 직접 만든 데이터 없이는 검증할 수 없다.
4. **수집본을 보관하지 않으면 재분석이 안 된다 (D6).** v3은 "수집본 보관 기본 꺼짐"인데, 그러면 도구가 업데이트돼 파서가 좋아져도 예전 점검을 다시 분석할 수 없고, 전문가에게 넘길 원자료도 없다. 반대로 켜 두면 레지스트리 하이브 등 개인정보가 많은 파일이 USB에 쌓인다. 결정이 필요하다.

## 4. 이 작업 환경의 한계

- 작업 환경은 Linux다. **Windows에서 실행해 볼 수 없다.**
- Windows용 빌드 도구를 내려받는 주소가 막혀 있어 **Windows 실행 파일(.exe)을 만들지 못했다.** 대신 GitHub에 올리면 Windows에서 자동으로 빌드·테스트하고 실행 파일을 내려받게 해 주는 설정(`.github/workflows/ci.yml`)을 넣었다. 직접 빌드하려면 Windows에 Rust를 설치하고 `cargo build --release -p st-cli`를 실행한다.
- 따라서 화면(GUI), 관리자 권한 상승, 잠긴 파일 읽기처럼 **Windows에서만 확인할 수 있는 기능은 이 환경에서 "완료"할 수 없다.**
